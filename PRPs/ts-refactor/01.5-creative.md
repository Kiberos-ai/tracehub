# Creative Exploration: TracHub TS Refactor — Traffic Control & Abuse Protection

## Idea DNA
```yaml
what: "Refactor TracHub to TS (Hono+Drizzle+Bun) with traffic control — long-poll/webhook to reduce server load, auto-ban for runaway clients"
why: "Current periodic polling (30s) wastes traffic when nothing changes; no protection against misbehaving SDKs flooding the server"
who: "Developers running polyglot services with checktrace/tracehub SDK"
constraints:
  - "Must use long-poll or webhook — NOT periodic polling — to reduce traffic"
  - "Must auto-detect and temporarily ban runaway clients (429 + Retry-After)"
  - "Backward compatible with existing checktrace 0.3.0 SDK (graceful degradation)"
  - "Zero-downtime migration from Python server"
success_criteria:
  - "/tracing/config requests reduced by 90%+ vs current periodic polling"
  - "Runaway client auto-banned within 10s, ban lasts 1-5 minutes, clear error message"
  - "Normal SDK clients never see 429 under standard operation"
```

## User Constraint (from user)
> "обязательно надо применять технологии longpoll/webhook для того чтобы снизить трафик на сервер, но также и если кто-то потерял контроль и сошел с ума - временно банить с соответствующим ответом"

Два жёстких требования:
1. **Long-poll или webhook** — periodic polling запрещён как primary mechanism. Клиент НЕ должен слать запросы каждые N секунд когда ничего не изменилось.
2. **Auto-ban runaway clients** — если SDK зациклился / сломан / кто-то пишет свой клиент и flooding сервер → временный бан с понятным ответом (429 + Retry-After + причина).

## Research Findings

### Long-Poll Pattern (RFC 7240 `Prefer: wait`)
- Клиент отправляет `GET /tracing/config` с `If-None-Match: "{etag}"` и `Prefer: wait=30`
- Сервер держит connection до: (a) конфиг изменился → 200 + новый конфиг, (b) timeout → 304 Not Modified
- Клиент сразу переподключается → новый long-poll цикл
- **Результат:** 0 запросов когда ничего не меняется (vs текущие ~2 req/min per SDK)
- Bun/Hono легко держат тысячи held connections — event loop не блокируется
- [Inferable.ai](https://www.inferable.ai/blog/posts/postgres-nodejs-longpolling.mdx) использует тот же паттерн для сотен worker nodes
- [RFC 7240 Prefer: wait](https://www.brendanlong.com/rfc-7240s-prefer-wait-instead-of-timeout-header.html) — стандартный HTTP механизм

### Rate Limiting & Ban в Hono
- [hono-rate-limiter](https://github.com/rhinobase/hono-rate-limiter) — community middleware, in-memory + Redis stores
- Key generation: IP + SDK client_id (не только IP — за NAT много клиентов с одного IP)
- [Best practice](https://dev.to/fiberplane/an-introduction-to-rate-limiting-3j0): layered limits — global coarse (IP) + fine-grained (client_id per endpoint)
- `throw new HTTPException(429)` в Hono — stops middleware chain immediately
- `Retry-After` header обязателен в 429 response — клиент знает когда retry
- [Behavioral detection](https://fiberplane.com/blog/rate-limiting-intro/): не только counts — паттерн "одинаковый endpoint 100x/min" = abuse

### Webhook Pattern (альтернатива long-poll)
- Сервер шлёт POST на registered callback URL когда конфиг изменился
- Требует: (a) клиент имеет HTTP-сервер, (b) регистрация webhook URL, (c) retry при недоступности
- Для SDK внутри application process — неудобно (нужен слушающий порт)
- Подходит для machine-level collector (Model A), но не для in-process SDK (Model B)

## Approaches

### A: Long-Poll Config + SDK Backpressure (Recommended)

**Description:** SDK отправляет `GET /tracing/config` с `If-None-Match` + `Prefer: wait=30`. Сервер держит connection до изменения конфига или timeout. Для ingest — обычный batch POST с server-side rate limiting и auto-ban.

**Mechanism:**
```
SDK                              TracHub Server
 │                                     │
 │── GET /tracing/config ─────────────>│
 │   If-None-Match: "42"               │  (holds connection up to 30s)
 │   Prefer: wait=30                   │
 │                                     │
 │   ... config changes (mark_hot) ... │
 │                                     │
 │<── 200 {mode, hot_correlations} ────│  (immediate push)
 │   ETag: "43"                        │
 │                                     │
 │── GET /tracing/config ─────────────>│  (SDK reconnects instantly)
 │   If-None-Match: "43"               │
 │   Prefer: wait=30                   │
 │                                     │
 │   ... 30s pass, nothing changed ... │
 │                                     │
 │<── 304 Not Modified ────────────────│  (timeout, reconnect)
 │                                     │
```

**Server implementation (Hono):**
- `waiters` Map: `etag → Promise<void>` resolve chain
- При `mark_hot()` / `cooldown_tick()` → resolve all waiters → they return 200
- Timeout: `Promise.race([configChanged, sleep(30s)])` → 304 if timeout wins
- `c.req.header("Prefer")` → parse `wait=N`, cap at 60s

**Backpressure на ingest:**
- Sliding window rate limiter per `client_id` (from `X-TraceHub-Client` header) или per IP
- Normal: 100 req/min per client → OK
- Warning: 200 req/min → 429 + `Retry-After: 5`
- Ban: 500 req/min sustained → 429 + `Retry-After: 60` + `X-TraceHub-Ban: temporary` + тело: `{"error": "rate_limit_exceeded", "message": "Client temporarily banned: excessive request rate", "ban_seconds": 60, "retry_after": 60}`

**Pros:**
- Нулевой трафик при стабильном конфиге (только held TCP connections)
- Мгновенная реакция на HOT-активацию (<1s vs текущие 0-30s)
- Стандартный HTTP — работает через все proxies, debuggable curl'ом
- Backward compatible: старый SDK без `Prefer: wait` получает обычный 200/304 ответ мгновенно
- Сервер контролирует когда "отпустить" клиента — natural backpressure

**Cons:**
- Held connections потребляют fd (file descriptors) — ~100 bytes RAM per connection, Bun держит тысячи
- Reverse proxy timeout: Traefik/nginx могут закрыть idle connection до server timeout → нужен `proxy_read_timeout 35s`
- Reconnection storm если сервер рестартует — все clients переподключаются одновременно → jitter на reconnect (0-5s random delay)

**Complexity:** medium
**Risk:** low — паттерн проверен (Inferable.ai, Fanout.io, CometD, и т.д.)
**Best for:** наш сценарий (5-50 SDK clients, low frequency config changes, in-process SDK)

### B: Server-Push Config via SSE Persistent Channel

**Description:** SDK устанавливает SSE connection к `GET /tracing/config/stream`. Сервер пушит config updates как SSE events. Для ingest — аналогично Approach A (batch POST + rate limiting).

**Mechanism:**
```
SDK                              TracHub Server
 │                                     │
 │── GET /tracing/config/stream ──────>│  (SSE connection opens)
 │   Accept: text/event-stream         │
 │                                     │
 │<── data: {full config} ─────────────│  (initial state)
 │                                     │
 │<── : ping ──────────────────────────│  (heartbeat every 15s)
 │                                     │
 │   ... mark_hot("corr-123") ...      │
 │                                     │
 │<── data: {delta: hot_add corr-123} ─│  (instant push)
 │                                     │
 │<── : ping ──────────────────────────│  (heartbeat)
 │                                     │
```

**Server implementation (Hono):**
- `streamSSE(c, async (stream) => { ... })` — native Hono helper
- Subscriber set: `Set<SSEStream>` — broadcast on config change
- Heartbeat: `setInterval(() => stream.write(": ping\n\n"), 15_000)`
- `stream.onAbort()` → remove from subscriber set (cleanup)
- Delta events: `event: config_update`, `data: {hot_add/hot_remove/mode_change}`

**Pros:**
- Истинный server-push — ноль polling, ноль held request/response cycles
- Самый низкий latency: event доходит в момент изменения (< 50ms)
- Hono `streamSSE` — first-class support, проще чем ручной long-poll
- Можно слать delta updates (только изменение, не весь конфиг)

**Cons:**
- **Persistent connection per SDK client.** 50 SDK → 50 постоянных SSE connections. При рестарте сервера — все reconnect одновременно.
- **Не backward compatible.** Текущий checktrace 0.3.0 не поддерживает SSE — нужен новый endpoint + старый periodic poll остаётся для legacy.
- **SDK сложнее.** SSE client в фоновом потоке / async task — EventSource в браузере тривиален, но в Python daemon thread + HTTP streaming = больше кода чем long-poll.
- **Traefik buffering.** SSE требует `X-Accel-Buffering: no` + правильные headers. Уже работает для `/traces/{corr_id}/stream`, но добавляется второй SSE endpoint.
- **Двойной протокол:** SSE для config push + HTTP POST для ingest = два разных transport механизма в одном SDK.

**Complexity:** medium-high
**Risk:** medium — SSE в SDK (не браузере) менее стандартен; два протокола увеличивают поверхность ошибок
**Best for:** сценарий с частыми config changes и требованием <100ms latency на config push

### C: Webhook Notify + On-Demand Pull

**Description:** SDK регистрирует callback URL при старте. Сервер шлёт POST на callback когда конфиг меняется. SDK обновляет внутренний кеш. Между уведомлениями — ноль трафика.

**Mechanism:**
```
SDK (startup)                    TracHub Server
 │                                     │
 │── POST /tracing/register ──────────>│  (register callback)
 │   {callback_url: "http://           │
 │    localhost:9199/tracehub-hook",    │
 │    client_id: "svc-manager-01"}     │
 │                                     │
 │<── 200 {config, lease_ttl: 300} ────│  (initial config + lease)
 │                                     │
 │   ... mark_hot("corr-123") ...      │
 │                                     │
 │<──────────── POST callback_url ─────│  (server pushes to SDK)
 │   {event: "config_changed",         │
 │    hot_add: ["corr-123"]}           │
 │                                     │
 │── 200 ──────────────────────────────│  (SDK acks)
 │                                     │
 │   ... lease expires in 5 min ...    │
 │                                     │
 │── POST /tracing/renew ────────────>│  (re-register every 5 min)
 │                                     │
```

**Pros:**
- Истинный zero-traffic между events — даже held connection нет
- Масштабируется для тысяч клиентов (server просто шлёт POST, не держит connections)
- Webhook — стандартный паттерн, понятный всем

**Cons:**
- **SDK должен слушать HTTP порт.** In-process SDK внутри FastAPI/Hono app — нужен отдельный порт или route на существующем сервере. Не все приложения — HTTP-серверы (CLI tools, workers, scripts).
- **NAT / firewall.** Сервер должен достучаться до callback URL. Если SDK за NAT / в Docker без exposed port → webhook не дойдёт.
- **Reliability.** Сервер должен retry webhook если SDK временно недоступен. Нужна очередь + retry + dead letter. Значительная серверная сложность.
- **Lease management.** Нужен TTL + re-registration чтобы не слать webhooks мёртвым клиентам. Доп. complexity.
- **Port conflicts.** Если 5 SDK на одной машине — каждый на своём порту для callback.

**Complexity:** high
**Risk:** high — NAT/firewall проблемы, reliability, port conflicts
**Best for:** machine-level collector (Model A из idea doc) с выделенным процессом и известным адресом. Не подходит для in-process SDK.

## Abuse Protection: Temporary Ban Architecture

Это ортогональная к выбору A/B/C система — применяется независимо от механизма config delivery.

### Threat Model
| Threat | Cause | Impact |
|--------|-------|--------|
| SDK in infinite loop | Bug: retry без backoff, config poll зациклен | Floods /tracing/config или /ingest |
| Custom client abuse | Кто-то написал свой клиент без rate limiting | Same as above |
| SDK version mismatch | Старый SDK без adaptive tracing шлёт 100% traces в COLD | /ingest overload |
| Replay attack | Replay captured /ingest requests | DB bloat |

### Three-Tier Response

**Tier 1: Rate Limit (soft)** — per client_id per endpoint
- `/ingest`: 120 req/min (2 req/s — нормальный batch sender)
- `/tracing/config`: 10 req/min (long-poll = ~2 req/min normally, periodic poll fallback = 2 req/min)
- `/traces/*` query endpoints: 60 req/min
- При превышении → `429 Too Many Requests` + `Retry-After: 5`

**Tier 2: Warning Ban (escalation)** — sustained abuse
- Если client_id получил 10+ rate-limit 429 за последние 2 минуты → warning ban
- Все запросы от client_id → `429` + `Retry-After: 60` + тело:
```json
{
  "error": "temporary_ban",
  "message": "Client temporarily banned: sustained rate limit violations. Check SDK configuration.",
  "ban_seconds": 60,
  "retry_after": 60,
  "client_id": "svc-manager-01",
  "violations": 15,
  "hint": "If using checktrace SDK, ensure adaptive_tracing=true and batch_size >= 10"
}
```
- Бан 60 секунд, потом автоматически снимается

**Tier 3: Hard Ban (repeat offender)** — repeated warning bans
- Если client_id получил 3+ warning бана за последний час → hard ban 5 минут
- Тот же 429 response, но `ban_seconds: 300` и `message` включает "repeated violations"
- После hard ban — counter сбрасывается, клиент может попробовать снова

### Client Identification
- **Primary key:** `X-TraceHub-Client` header (формат: `{hostname}:{project_name}:{source_id}`)
- **Fallback:** IP address (для клиентов без header — legacy SDK)
- **Per-IP coarse limit:** 1000 req/min total (safety net за NAT)
- SDK TS/Python ВСЕГДА ставит `X-TraceHub-Client` → fine-grained per-client tracking

### Implementation: In-Memory Sliding Window
```
Map<client_id, {
  windows: Map<endpoint_group, { timestamps: number[], violations: number }>,
  ban_until: number | null,       // Unix ms, null = not banned
  ban_tier: 0 | 1 | 2,           // 0=ok, 1=warning, 2=hard
  warning_ban_count: number,      // count in last hour
  last_warning_ban_at: number,    // for hourly reset
}>
```
- Cleanup: every 60s, remove entries with no activity in last 10 min
- При рестарте сервера — все баны сбрасываются (in-memory, OK — клиент получит чистый старт)

### SDK Response to 429
SDK MUST:
1. Прочитать `Retry-After` header
2. Остановить все запросы к серверу на `retry_after` секунд
3. НЕ drop'ать traces — буферизовать в памяти (до лимита, e.g. 10K entries)
4. После `retry_after` — resume с exponential backoff (retry_after × 1, × 2, × 4, cap 5 min)
5. Логировать warning в stderr: `[TracHub] Rate limited by server, retrying in {N}s`

SDK MUST NOT:
- Retry немедленно (это и есть "runaway" behavior)
- Ignore 429 и продолжать слать
- Crash или бросить exception в user code

## Recommendation

**Selected:** Approach A — Long-Poll Config + SDK Backpressure + Three-Tier Abuse Protection

**Justification:**
Long-poll даёт 95%+ traffic reduction при минимальной сложности — это обычный HTTP GET с задержанным ответом. Backward compatible с существующим checktrace 0.3.0 (просто не отправляет `Prefer: wait` → получает мгновенный ответ как сейчас). Портирование на любой язык тривиально — нужен только HTTP client с configurable timeout. SSE (B) даёт чуть лучший latency (<50ms vs <1s), но за счёт усложнённого SDK (SSE parser в фоновом потоке) и отсутствия backward compatibility — не оправдано для нашего сценария, где config меняется редко (несколько раз в час при debug). Webhook (C) отпадает — SDK внутри приложения не должен слушать порт.

**Trade-offs accepted:**
- Config change latency <1s (не <50ms как SSE) — приемлемо, т.к. config меняется при debug-запросах, 1s задержка незаметна
- Held connections (N open TCP per server) — при 50 SDK это ~5KB RAM, Bun обрабатывает десятки тысяч concurrent connections

**Key decisions for PRD:**
1. **Long-poll** на `GET /tracing/config` с `Prefer: wait=N` (cap 60s) + `If-None-Match`
2. **Three-tier abuse protection:** rate limit → warning ban (60s) → hard ban (300s), in-memory, per `X-TraceHub-Client`
3. **SDK MUST:** honour `Retry-After`, buffer traces during ban, exponential backoff
4. **SDK MUST:** send `X-TraceHub-Client: {hostname}:{project}:{source_id}` header on every request
5. **Backward compatibility:** старый SDK без `Prefer` header → обычный мгновенный 200/304 response (no regression)
6. **Reconnect jitter:** SDK adds random 0-5s delay before reconnecting long-poll after disconnect/timeout (prevent thundering herd on server restart)
