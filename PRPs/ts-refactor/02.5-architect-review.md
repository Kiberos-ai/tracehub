## Phase B: Seven-Pillar Evaluation

### 1. SSOT — Single Source of Truth

**Rating: PASS**

The PRD correctly identifies:
- Drizzle schema as the SSOT for DB structure (AC-23)
- Zod schemas for request/response validation (Technical Notes)
- In-memory state for adaptive tracing (REQ-12, CN-01)
- `X-TraceHub-Client` header format defined once (DB-07)

The SSOT duplicate field names (correlation_id, source_id, etc.) are resolved by the rewrite: Zod schema defines the trace entry type once, Drizzle schema mirrors it for DB, and both are in the same codebase.

**One concern:** The PRD defines rate limit thresholds inline in AC-08 (`/ingest` 120 req/min, `/tracing/config` 10 req/min, `/traces/*` 60 req/min) AND again in REQ-20 with identical values. This is fine as requirements-to-AC traceability, not a SSOT violation — implementation will define them as named constants once.

### 2. SCALE — Scalability & Performance

**Rating: CONCERN**

**What's good:**
- NFR-01 (<10ms config response, in-memory) is realistic and correct
- NFR-02 (<50ms batch ingest of 100 traces with WAL) aligns with Bun SQLite benchmarks
- NFR-03 (200+ concurrent long-poll) is well within Bun's capability
- Per-IP coarse limit (REQ-24, 1000 req/min) is a sensible safety net

**Concerns:**

**(B-SCALE-1) MAJOR — Long-poll waiter set has no upper bound.** PRD says "Server maintains `Set<{resolve, etag}>` of waiting clients" (Technical Notes) and NFR-03 targets 200+ concurrent. But there is no `MAX_CONCURRENT_LONGPOLL` cap defined. If 500 clients connect simultaneously (e.g., after server restart with thundering herd), the server accepts all. The idea doc mentions "Limit max concurrent long-poll connections (e.g., 200)" in Known Gotchas #3, but this did NOT make it into the PRD requirements.

**Fix:** Add REQ-XX: "Server SHALL cap concurrent long-poll connections at `MAX_LONGPOLL_CONNECTIONS` (env, default 200). New connections beyond cap receive immediate 200 response (fallback to periodic poll behavior)."

**(B-SCALE-2) MINOR — No DB size / row count monitoring.** NFR-09 caps memory at 128MB but there's no guidance on DB size limits or alerting. Current Python server has `/stats` with `db_size_mb` which is good. The 24h retention (TRACEHUB_RETENTION_HOURS) handles cleanup, but at high ingest rates (10 req/s * 10 traces/batch = 100 traces/s = 8.6M rows/day), SQLite performance degrades. This is an operational concern, not a PRD requirement — but worth noting. Current scale (909K traces/day per idea doc) is fine.

### 3. CLEAN — Clean Architecture & Separation of Concerns

**Rating: PASS**

The PRD correctly separates:
- Server (Hono + Drizzle) — well-defined module boundaries
- TS SDK (`@tracehub/sdk`) — separate package, zero deps
- Python SDK (checktrace 1.0.0) — separate package

The stack choices are idiomatic:
- Hono middleware for abuse protection (REQ-20-24) — correct pattern
- Drizzle for DB layer — correct for type-safe SQLite
- Zod for validation — integrates with Hono middleware

**One note:** The PRD doesn't explicitly define module structure for the TS server (e.g., routes, middleware, state, db as separate modules). This is fine — the PRD defines WHAT, not HOW to organize files. The plan phase should define module structure.

### 4. EXTEND — Extensibility & Open-Closed

**Rating: PASS**

Good extensibility decisions:
- DB-05 (in-memory abuse protection) — easy to swap to Redis later (explicitly noted in Out of Scope)
- DB-06 (Model B, no collector) — collector can be added later (explicitly noted in Out of Scope)
- Long-poll design — adding new config fields doesn't change the delivery mechanism
- `X-TraceHub-Client` header — extensible format `{hostname}:{project}:{source_id}`

The PRD explicitly lists future extensions in Out of Scope with "deferred" labels, which is correct.

### 5. CONFIG — Configuration & Environment Awareness

**Rating: CONCERN**

**What's good:**
- DB-01 through DB-09: all architectural decisions documented and justified
- Env vars for adaptive tracing (preserved from Python: `ADAPTIVE_HOT_TTL`, etc.)
- `TRACEHUB_SECRET` env var for auth
- `TRACEHUB_PORT` env var for port

**Concerns:**

**(B-CONFIG-1) MAJOR — DB path configuration missing from PRD.** CONFIG-001 scan finding: current Python uses `TRACEHUB_DB` env with `/tmp/tracehub.db` default. PRD AC-22 mentions "bun:sqlite sync driver" but never defines where the DB file lives. This is critical for Docker deployment — the DB must be on a mounted volume, not in the container's ephemeral filesystem.

**Fix:** See Amendment A1.

**(B-CONFIG-2) MINOR — Rate limit thresholds not env-configurable.** REQ-20 hardcodes rate limits (120/10/60 req/min). These should be env-configurable with the PRD values as defaults. At scale, operators need to tune these without rebuilding.

**Fix:** Add note to REQ-20: "Rate limits SHALL be env-configurable (`TRACEHUB_RATE_INGEST`, `TRACEHUB_RATE_CONFIG`, `TRACEHUB_RATE_QUERY`) with stated values as defaults."

**(B-CONFIG-3) MINOR — Ban durations not env-configurable.** DB-09 fixes warning=60s, hard=300s. Same argument as B-CONFIG-2.

### 6. ERROR — Error Handling & Observability

**Rating: CONCERN**

**What's good:**
- NFR-07: server logs ban events to stderr (structured format defined)
- AC-12: ban response body is well-specified (error, message, ban_seconds, retry_after, client_id, violations, hint)
- CN-03: SDK must not crash on TracHub failure
- REQ-29: SDK honours Retry-After with backoff

**Concerns:**

**(B-ERROR-1) MAJOR — No SDK-side logging requirement.** The PRD defines server-side logging (NFR-07) but SDK logging is unspecified beyond CN-03 ("fail silently"). The creative exploration says "SDK MUST: log warning to stderr: `[TracHub] Rate limited by server, retrying in {N}s`" but this did NOT make it into the PRD requirements.

**Fix:** See Amendment A2.

**(B-ERROR-2) MINOR — No server startup validation logging.** PRD doesn't require the server to log its configuration on startup (DB path, port, retention, secret presence, WAL mode confirmation). This is standard observability practice.

**Fix:** Add NFR-XX: "Server SHALL log configuration summary on startup: port, DB path, WAL mode, retention hours, secret configured (yes/no)."

**(B-ERROR-3) MINOR — insert_trace error swallowing.** Current Python `db.py:115` has bare `except: return False`. PRD doesn't address DB error handling strategy. The TS rewrite should log DB errors (constraint violations are expected for dedup, but actual I/O errors should be logged).

### 7. CONTRACT — API Contracts & Backward Compatibility

**Rating: PASS**

This is the strongest part of the PRD:
- AC-15: "All existing endpoints work identically (same JSON request/response contract)"
- CN-05: "Server must NOT break checktrace 0.3.0 SDK requests"
- NFR-06: "TS server SHALL accept requests from checktrace 0.3.0 SDK without any client changes"
- AC-05: backward compat for clients without `Prefer` header
- AC-39: "Existing checktrace 0.3.0 SDK works unchanged against TS server"
- Migration path is well-defined (Technical Notes, 4 steps)

**One minor note:** The PRD doesn't define what happens when checktrace 0.3.0 (no `X-TraceHub-Client` header) hits the rate limiter. REQ-20 says "fallback: IP" which is correct, but AC-14 (per-IP coarse limit 1000 req/min) is very generous — a single legacy client behind NAT sharing IP with legitimate clients could cause collateral banning. This is an acceptable trade-off at current scale (5-50 clients) but worth noting.

## Phase C: Additional Checks

### C1: SSOT Semantic Compliance

**PASS.** The PRD maintains semantic SSOT:
- Trace entry schema defined once (Zod) and mirrored to Drizzle
- Rate limit values defined once with AC-to-REQ traceability
- Adaptive tracing parameters (HOT/WARM/COLD timers) referenced from existing codebase (DB-08)
- Ban durations defined once (DB-09)

### C2: Scalability Stress Test

**10x (500 clients, 100 traces/s ingest):**
- Long-poll: 500 held connections. Bun handles this easily (tested to 10K+). But needs the MAX_LONGPOLL_CONNECTIONS cap (B-SCALE-1).
- Ingest: 100 traces/s = 6000/min. At batch size 10, that's 600 req/min across all clients. Rate limit per client is 120 req/min — with 500 clients, total is ~1.2 req/min/client. Well within limits.
- SQLite: 100 inserts/s in WAL mode with batch transactions — no problem (Bun SQLite benchmarks show 28ms for 10K inserts).
- Memory: 500 client rate-limit entries in abuse protection Map ~ 500KB. Well under 128MB.

**100x (5000 clients, 1000 traces/s ingest):**
- Long-poll: 5000 held connections. Bun can handle this, but needs investigation on fd limits and memory per connection.
- SQLite: 1000 inserts/s sustained — this is where single-file SQLite starts to show strain. WAL helps but 100x would need PostgreSQL or sharding. PRD correctly defers this (Out of Scope: "Local collector — deferred, add later if >10 services per machine").
- Abuse protection cleanup loop: iterating 5000 entries every 60s — negligible.
- **Verdict:** PRD is designed for 5-50 clients (stated in DB-05). 100x would require architectural changes (PostgreSQL, horizontal scaling) which are correctly out of scope.

### C3: Change Scenario Test

**New language SDK (e.g., Go):**
- Protocol is plain HTTP JSON — trivial to implement
- Long-poll is standard HTTP GET with timeout — no SDK-specific server changes
- `X-TraceHub-Client` header format is documented (DB-07)
- Abuse protection works per-client-header — auto-compatible
- **Verdict: PASS** — new SDK requires zero server changes

**New trace field (e.g., `span_id`):**
- Drizzle schema change + migration
- Zod schema update
- SDK update to accept new field in `checkpoint()`
- Backward compat: field is optional, old SDKs don't send it, INSERT handles NULL
- **Verdict: PASS** — standard schema evolution

**New environment (e.g., Kubernetes with 100 pods):**
- DB path: needs volume mount (currently missing from PRD — see A1)
- Rate limiting per-client works (each pod has unique hostname in `X-TraceHub-Client`)
- Long-poll: 100 held connections — fine
- **Verdict: PASS** — no architectural changes needed, but DB path must be configurable

## Amendments Required

### A1: DB Path Configuration (MAJOR)

**Add to Requirements, after REQ-09:**

> **REQ-XX** Server SHALL read DB path from `TRACEHUB_DB` env var (default: `./data/tracehub.db`). The default MUST NOT be in `/tmp/` or any volatile filesystem.

**Add to Scope (In Scope):**

> Ensure Docker volume mount for `./data/` directory in docker-compose.yml

**Rationale:** CONFIG-001 scan finding. `/tmp/tracehub.db` is volatile — data lost on reboot. Docker deployment requires a mounted volume. The Python server already uses `TRACEHUB_DB` env var; the TS server must preserve this.

### A2: SDK Logging Requirements (MAJOR)

**Add to Requirements, after REQ-30:**

> **REQ-XX** SDK SHALL log operational events to stderr (not throw): rate-limit received, ban received, connection lost, reconnect attempt, backoff timer. Format: `[TracHub] {event}: {details}`.

> **REQ-XX** SDK SHALL accept an optional `logger` callback in `init(config)` for applications that want to redirect TracHub SDK logs (default: `console.warn`).

**Rationale:** ERROR-001 scan finding + creative exploration specified this but PRD omitted it. Without SDK logging, operators cannot diagnose why traces are not arriving.

### A3: SDK Graceful Shutdown (MINOR)

**Add to AC-32 detail:**

> `close()` SHALL flush pending traces with a timeout (default 5s). If flush does not complete within timeout, drop remaining traces and return. `close()` MUST NOT block indefinitely.

**Rationale:** CONFIG-005 scan finding. Current Python SDK has `thread.join(timeout=2.0)` — the TS SDK needs equivalent bounded shutdown.

### A4: Long-Poll Connection Cap (MAJOR)

**Add to Requirements, after REQ-18:**

> **REQ-XX** Server SHALL cap concurrent long-poll connections at `MAX_LONGPOLL_CONNECTIONS` (env, default 200). Connections beyond cap SHALL receive immediate 200 response with current config (graceful degradation to periodic poll).

**Rationale:** B-SCALE-1. Idea doc's Known Gotchas #3 identified this but it was not carried into the PRD. Without a cap, server restart with many clients causes unbounded connection accumulation.

### A5: Server Startup Logging (MINOR)

**Add NFR:**

> **NFR-XX** Server SHALL log configuration summary on startup to stderr: bind address, port, DB path, WAL mode status, retention hours, secret configured (yes/no), max long-poll connections.

**Rationale:** B-ERROR-2. Standard observability practice for debugging deployment issues.

## Verdict

**CONDITIONAL APPROVAL**

The PRD is well-structured, thorough, and demonstrates strong architectural thinking. The decision boundaries (DB-01 through DB-09) are well-justified. The backward compatibility story (CN-05, NFR-06, AC-39) is the strongest aspect. The abuse protection design (three-tier, per-client) is sound and proportionate.

**Conditions for full approval (must be applied before planning):**

1. **A1** (MAJOR) — Add `TRACEHUB_DB` env var requirement with non-volatile default
2. **A2** (MAJOR) — Add SDK logging requirements
3. **A4** (MAJOR) — Add long-poll connection cap requirement

**Recommended but not blocking:**

4. **A3** (MINOR) — Specify SDK `close()` timeout behavior
5. **A5** (MINOR) — Add server startup logging NFR
6. **B-CONFIG-2** (MINOR) — Make rate limit thresholds env-configurable
7. **B-CONFIG-3** (MINOR) — Make ban durations env-configurable

All three MAJOR conditions are straightforward additions (1-2 sentences each) that fill gaps between the creative exploration and the PRD. No architectural rework required. Once applied, the PRD is ready for planning.
