## 5. Ambiguity Detection

### 5.1 Resolved -- No Issues

- All env var names, defaults, and types are specified in Task 0.
- All API response shapes are traced to "match Python endpoints.py exactly."
- Ban escalation logic (thresholds, durations, reset conditions) is fully specified in Task 7.
- Dedup logic (5min window, UPSERT condition) is specified in Task 1.

### 5.2 Minor Ambiguities Found

**AMB-01: SSE event format for trace streaming (Task 6)**
The plan says "Send existing traces first (query DB), subscribe to new traces" but does not specify the SSE `event:` type or `data:` JSON format. The PRD says "stream traces via SSE" (REQ-05) but also does not specify the event payload format. The plan should reference the existing Python `streaming.py` format as the canonical contract.
**Risk:** Low -- implementation will naturally match Python by reading `streaming.py`.
**Action:** None required -- "match Python 1:1" covers this implicitly.

**AMB-02: GET /recent rate limit implementation (Task 3)**
REQ-07 says "rate limiting (30 req/min)" for `/recent`. Task 7's three-tier system groups `/recent` under "query" at 60 req/min. The per-endpoint 30 req/min from REQ-07 is mentioned in Task 3 as "rate limit (30 req/min internal)" but the mechanism is unclear -- is this a separate in-route limit or delegated to the rate-limit middleware? The middleware (Task 7) uses 60 req/min for the query group.
**Risk:** Medium -- two different rate limits for overlapping endpoints could conflict.
**Action needed:** Clarify whether `/recent` has its own 30 req/min limit (in addition to the query group 60 req/min) or if the middleware group limit should be 30 for `/recent` specifically.

**AMB-03: Drizzle migration strategy for existing data (Task 1)**
The idea doc mentions "one-time migration: export current schema -> create baseline migration in Drizzle" (gotcha #6). Task 1 says `initDb() -- run migrations or ensure table exists` but does not detail how existing SQLite databases (from the Python server) are handled during the transition. If the TS server starts against an existing Python-created DB file, does it run Drizzle migrations? Or does it detect the existing schema?
**Risk:** Medium -- wrong migration strategy could wipe existing trace data on first TS server start.
**Action needed:** Task 1 should explicitly address: (a) Drizzle introspect/pull from existing DB to create baseline, OR (b) `CREATE TABLE IF NOT EXISTS` without Drizzle migrations for v1, with migrations for future schema changes.

**AMB-04: SDK `close()` behavior -- pending long-poll request**
AC-32 says `close()` flushes pending traces with 5s timeout. Task 10 mentions `config-poll.ts close() -> abort current fetch, stop loop`. However, the interaction between a pending long-poll fetch (which blocks for up to 30s) and `close()` is not specified. Does `close()` use `AbortController.abort()` on the pending fetch?
**Risk:** Low -- standard pattern is AbortController, but should be explicit.
**Action:** Minor -- confirm AbortController usage in implementation.

**AMB-05: DELETE /cleanup endpoint auth**
Task 3 lists `DELETE /cleanup` under admin.ts. The PRD does not specify whether this endpoint requires auth (X-TraceHub-Secret). The current Python server's cleanup is automated (lifespan loop), but the endpoint could be dangerous if unauthenticated.
**Risk:** Low -- cleanup deletes old traces, not current ones.
**Action:** Consider applying auth middleware to admin endpoints.
